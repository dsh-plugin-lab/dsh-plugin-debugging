# 写侧工具的工具边界：分离为主，三处内聚

**日期**：2026-10-13 ｜ **状态**：已定（v1.1 实现按此执行）

## 背景

v1.1 要加两个**写侧**工具（`dsh_hot_reload` / `dsh_restart`）。维护者提出一组边界问题：

> 重启工具重启之后要不要**自动激活会话**？返回给会话要不要**返回当前状态**？当前状态是不是**从别的工具那里调用**（包含关系）？还是**分离** —— 工具只负责动作，要看状态由 Agent 自己去调那些只读小工具？

这不是风格问题：它决定 v1.1 的工具面形状，也决定失败模式长什么样。

## 决定

**分离为主**，契约是**三段**，不是一段：

| 阶段 | 谁负责 | 内容 |
|---|---|---|
| 调用时（进程还活着） | 写工具**同步返回** | **收据或拒绝**。拒绝时带**闸门证据**（它自己算出来的：哪几个会话在跑、哪条闸没过）——这是它做决定的依据，不是「状态报告」 |
| 重启后（新进程起来） | 新进程投一条 **notice** 回原会话 | **只放事实 + 指针**：什么时候重启的、停机多久、为什么、marker 已清；**不塞状态快照**，而是给「要看现在怎么样，调 X」 |
| 要看状态 | **Agent 自己调那四个只读工具** | 它们已是单一职责、可组合、可单独复核 |

**必须内聚的三处**（不能推给别的工具）：① **闸门输入**（`agents.list()` / `jobs.list()` / `workspace/session-activity` / bundle 表 / 启动命令）；② **marker 的写与清**；③ **唤醒**（进程已死，Agent 没机会自己发起 —— 但只叫醒 + 告知事实）。
一般化：**判定归判定工具，状态归只读工具，动作归写工具**；三者靠 `nextStep` 与 notice 串，**不靠嵌套**。

## 替代方案与被否的理由

1. **写工具内嵌调只读工具**（例如 `dsh_restart` 内部调 `dsh_check_effect_mode` + `dsh_diagnose_plugin_load` 生成状态报告）
   → **否**。① **失败模式相乘**：读超时/读不到时，重启该不该继续？会造出「因为诊断读失败所以没能重启」这种荒唐路径；② **闸门是安全属性**，必须原子、只依赖各自原始输入、不可被调用方绕过（与「没有 `force`」同一条理由）；③ 状态的正确读法是**新进程读**，而内嵌只能给旧进程读到的值。
2. **notice 里塞状态快照**
   → **否**。那是「当前状态」的**第二个 home**（违反「一处一事实」）；而且快照只是**开机瞬间**的值，反而会让模型以为它是最新的。
3. **唤醒话术强制「请继续」**（参考实现 `dsh-desktop-auto-restart` 的做法）
   → **否**，取 `dsh-smart-restart` 那种**信息性 notice**：重启后该不该继续是**语义判断**，工具没有足够上下文。我们把「要不要接着干」留给 Agent。
4. **两个写工具合并成一个「修好它」**
   → **否**。热重载可回滚、重启不可逆，闸门也不同；合并会让模型倾向选更重的那条路。

## 代价与重开条件

- **代价**：Agent 需要**多一次往返**（先调写工具、再调只读工具看现状）；notice 不带状态时，模型可能**不查就继续** —— 缓解手段是 notice 里给 `nextStep` 指针（指向具体该调哪个只读工具）。
- **重开条件**：若真机观察发现「notice 不带状态会导致模型普遍误判」，再考虑**有限内嵌**（只调一个只读工具、只取一个字段），并把该例外写进这里。
