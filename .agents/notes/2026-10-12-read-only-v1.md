# v1 只有只读工具：为什么把 `dsh_restart` / `dsh_hot_reload` 推到 v1.1

状态：生效

> **后续（2026-10-13）**：本决策的**重开条件已部分兑现** —— v1.1 引入了 `dsh_hot_reload`（写侧，**就地换模块、失败放回**），
> 它**不杀进程**，因此仍在本决策划定的红线内；`dsh_restart`（唯一会杀宿主的那个）**仍然推迟**，排在最后。
> 「诊断半边只读」这条**没有变**，且由 `test/redlines.test.ts` 的 B10 守着；写侧边界由 B15 守着。
> **本文件是 2026-10-12 的历史记录，不回改** —— 现状见 [docs/SHAPE.md](../../docs/SHAPE.md) 与 [AGENTS.md](../../AGENTS.md)。

**类型**：决策。

## 背景

排障的自然终点是「那就重启一下」。但本插件的**排障对象正在被使用**：
它会杀掉那个宿主进程，而宿主一死，**用插件自救的路也没了** ——
这是「工具会不会把自己赖以运行的环境拆掉」的问题，不是功能多少的问题。

关键的机制事实是：**`defineTool` 里没有任何审批字段**。
`DefineToolOptions` 的选项全集里没有 `require_approval` / `requireApproval`
（recon-C 命题 3：`[RTp]\dsh-tools\lib\types\schema.d.ts:178-240`），
全树 grep 这两个名字 **0 命中**（RT 与 CK 各一次）。审批是**另一条链路**：
`ctx.tools` 的 `'tools/pre-execute'` waterfall 事件返回 `{ kind: 'ask' }`，
宿主再经 **`ctx.approval`** 判定，且**只有 `'allowed-once'` 放行**
（recon-C 命题 3：`[RTp]\dsh-tools\lib\types\index.d.ts:47`、`:445-459`；
`[RTp]\dsh-user-approval\lib\types\index.d.ts:19-22`、`:131`、`:135`；
放行判定在 `[RTp]\dsh-tools\lib\types\index.js:1101-1134`）。

**结论**：不存在「给工具加个字段就安全了」这条路。
要让一个会杀宿主的工具安全，得先在**策略层**把语义定下来。

本机 web profile 的策略现状（只读实测 `~\.dsh\profiles\web\cordis.patch.yml`）：
`read-only` → `approval: ask`（`:77-79`）、`workspace-write` → `ask`（`:80-82`）、
`danger-full-access` → **`approval: never`**（`:83-85`），且 `defaultPreset: danger-full-access`（`:86`）。
即：**默认档位下没有人工确认这一步**。

## 决定

**v1 工具面 = 四个只读工具**：`dsh_check_effect_mode` / `dsh_diagnose_plugin_load` /
`dsh_check_auth` / `dsh_dump_config`。命名用 check / diagnose / dump，
与「只读」这个行为一致，并把动作类命名空间（restart / reload）**留给 v1.1**。

`dsh_restart` 与 `dsh_hot_reload` **推迟到 v1.1**，等产品语义四项定了再引入：
审批策略、冷却、失败恢复、权限边界。

## 替代方案与被否的理由

- **v1 就带副作用工具，靠 `tools/pre-execute` + `ctx.approval` 弹窗兜底** —— 被否。
  默认档位是 `danger-full-access / approval: never`（见上），这道门在**最可能被使用的档位上等于不存在**；
  而「档位是用户选的」不能当成设计依据 —— 插件不该把安全性押在别人没改配置上。
- **v1 带 `dsh_restart` 但只做 dry-run** —— 被否（不是错，是**不完整**）：
  dry-run 回答了「会发生什么」，却没有回答「失败了怎么恢复」；
  而一个只会说「我本可以重启」的工具对排障者的价值，低于把 kill 之后的恢复路径先想清楚。
  同一条理由也说明：dry-run 很可能是 v1.1 的**第一步**，而不是 v1 的替代品。
- **靠 `require_approval: true` 声明一个审批门** —— 被否，且值得单独记住：
  这个字段**不存在**（recon-C 命题 3）。经变量或 `any` 传进来时会被 `defineTool`
  **静默丢弃** → 工具**没有任何门**照常执行。把「有审批字段」写进设计文档，
  等于设计了一个不存在的门 —— 这是本决策里最贵的一条，因为它错在**心智模型**上。

## 代价与重开条件

**代价**：使用者遇到「宿主端代码改了」这类场景仍然要**手工重启**，
插件只能把「是否需要重启」判准并说清理由（`dsh_check_effect_mode` 的职责）。
这是有意的：v1 的承诺是**只读**。

**重开条件（四项全部有结论后，才动 v1.1）**：
1. **审批语义**：`tools/pre-execute` 返回 `ask` 之后，在真实 UI 与当前策略下到底发生什么。
2. **冷却**：连续重启请求的节流（避免排障循环把宿主反复杀掉）。
3. **失败恢复**：重启失败/半死时的退路。
4. **权限边界**：尤其是 `danger-full-access` 这一档下 `ask` 的实际行为。

**注意第 4 项的验证状态**：本仓 `AGENTS.md` 的「待办」记着「`danger-full-access` 档下 `ask`
会被确定性拒绝」；而 recon-C 的「② 源码读不出、必须真机运行才能定的项」第 3 条把
「审批门在真实 UI / 策略下的表现」明确列为**尚未实测**。两者对照看，
**这句话目前是待验证的判断，不是实测结论** —— 动手做 v1.1 之前必须先跑一次真机。
