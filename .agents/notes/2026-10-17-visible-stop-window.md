# 无窗口宿主的可见停止入口：为什么是「窗口持有 Job Object」

**日期**：2026-10-17 ｜ **状态**：生效

## 背景：修好一个缺陷，代价是拿走了唯一看得见的停止方式

本轮之前，重启宿主会**创建一个可见控制台**——那是缺陷（每次重启弹窗），修法是
`wscript` + 窗口样式 0（[SHAPE §6.1.1](../../docs/SHAPE.md)）。修完之后宿主彻底没有窗口了：

- 它的 `MainWindowHandle` 是 **0**（实测）；
- Web GUI **没有退出入口**（`appExit` 只存在于 `dsh-cmdline` / `dsh-headless`）；
- 于是用户**唯一的停止办法**变成「按端口找 pid 再强杀」：

  ```
  Stop-Process -Id (Get-NetTCPConnection -LocalPort 3080 -State Listen).OwningProcess -Force
  ```

这个代价在 PR #62 合并时就存在，由 issue #63 记录。本文是给它的解。

## 决策：一个可见窗口，它的**存在**就是停止按钮

**不**在宿主里加「退出」按钮，也**不**改 Web GUI（那是宿主的面）。做法是：

**让重启启动器另外拉起一个可见的控制台窗口，由它持有宿主所在的 Job Object 句柄。**
窗口结束（关掉 / Ctrl+C / 被强杀）⇒ 最后一个 job 句柄关闭 ⇒ 内核按
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 终结宿主。

### 为什么这个方法成立的**理由必须写清**

它不是「我们用某种方式杀了宿主」，而是：**内核在 job 的最后一个句柄关闭时终结成员**。
句柄由窗口进程持有，所以**任何**让窗口进程结束的方式都成立，包括：

| 怎么结束窗口 | 脚本里的 `finally` 跑不跑 | 宿主 |
|---|---|---|
| 点 X 关窗 | 跑 | 内核杀（实测 **0.3 s**） |
| **Ctrl+C** | 跑 | 内核杀（实测 ≤ 233 ms） |
| 任务管理器强杀 | **不跑** | 内核杀（实测 **0.3 s**） |

第三行是关键：它证明**不依赖脚本里任何一句代码**。这也是本仓从不接受「补一个 taskkill 兜底」
的原因——兜底会把「用户关掉一个他能看见的东西」换成「插件按 pid 杀一个进程」。

### 身份怎么定：按端口，不按命令行

多个 DSH 实例（3080 / 3081）要各绑各的。**命令行不可用**：真宿主的命令行是

```
"E:\nodejs\node.exe" ...\@deepseek-ai\dsh\lib\bin.js web
```

——没有 `--port`、没有 `--profile`、没有 `DSH_HOME`。所以身份用**端口**：作业文件里带
`stopWindowPort`，窗口轮询 `Get-NetTCPConnection -LocalPort <port>` 拿属主 pid，
并要求进程名是 `node`（不是就不绑定，避免关窗时误杀无关进程）。

两个实例实测互不影响：关掉 3081 的窗口，3081 的宿主死、3082 的宿主活着。

### 单例：N 次重启只有一个窗口

三层，都以端口为键：命名 mutex `Global\DshStopWindow-<port>`、pidfile、以及启动器在拉起
窗口**之前**先读 pidfile 并用 WMI 验活。实测连跑三次启动器 ⇒ 窗口数恒为 1。

## 落地形态：静态资产 + 一个作业文件

```
schtasks /tr  →  wscript.exe "<shim>" "<job 文件>"     ← GUI 子系统，保证零窗口
                    └─ sh.Run("node launcher.js <job>", 0)   ← 隐藏
                         ├─ 等旧 pid 退出（轮询，上限 = delayMs）
                         ├─ spawn 新宿主（windowsHide ⇒ CREATE_NO_WINDOW）
                         └─ wscript show-window.vbs "<job>"        ← 样式 1 = 可见
                              └─ powershell -File assets/stop-window.ps1 …  ← 持 job 句柄
```

四个静态资产（`assets/`，不再在运行期拼字符串）：

| 资产 | 职责 |
|---|---|
| `launcher.vbs` | 只做「GUI 子系统那一跳」：样式 0，隐藏 |
| `show-window.vbs` | 只做「开一个可见控制台」：样式 1 |
| `launcher.js` | 全部决策（等 pid / 起宿主 / 确保窗口），**可单测** |
| `stop-window.ps1` | 可见窗口：持 job 句柄、绑宿主、渲染面板 |

动态值走一个 `key=value` 的作业文件 `restart/launch-<port>.job`。

## 实测（2026-10-17，本机）

| # | 断言 | 结果 |
|---|---|---|
| 1 | 关窗口 ⇒ 宿主死 | 0.3 s |
| 2 | Ctrl+C ⇒ 宿主死 | ≤ 233 ms（200 ms 采样） |
| 3 | 强杀窗口 ⇒ 宿主死（`finally` 不跑） | 0.3 s |
| 4 | 已在别的 job 里的进程能否被收编 | 能（`inAnyJob=True`，嵌套 job 成立） |
| 5 | 双实例隔离 | 关 3081 的窗口，3082 的宿主活着 |
| 6 | 连跑三次启动器 | 窗口数 **1** |
| 7 | 全链路（`launcher.js` → 隐藏宿主 → 可见窗口绑定） | 成功，`stop-window.log` 三行齐全 |

## 替代方案（都试过或被否掉）

| 方案 | 为什么不用 |
|---|---|
| **`taskkill` / `Stop-Process` 脚本** | 要「执行到那一行」才算数：窗口被强杀、异常退出时**不会**执行。job 句柄关闭则一定发生 |
| **Ctrl+C 之外再补 `taskkill` 兜底** | 把机制从「内核动的手」降级成「我们的代码杀的」，且两份实现会漂 |
| **`powershell -WindowStyle Hidden`** | ConPTY 下管不到 Windows Terminal 的标签页，**实测仍会开窗口** |
| **在 Web GUI 加退出入口** | 那是宿主的面，不是插件的；`appExit` 在 web 载体上不可达 |
| **托盘图标** | 需要额外的常驻本体，比这个窗口更重；且它同样要一条「怎么真正停掉」的路 |
| **`node` 直跑当启动器（去掉 VBS）** | `node.exe` 是控制台程序，计划任务跑它**必开可见窗口**，而 `schtasks` 没有隐藏开关。VBS 无法删除，但已退化成无逻辑原语 |
| **Rust + napi-rs 原生模块** | 内核原语与现有实现**完全相同**（都是 job 对象），只换语言；代价是给一个零运行时依赖的诊断插件引入「import 期失败 ⇒ 八个工具一起静默消失」的新失败模式（坑 1 / 坑 12 的形态），并多出跨平台发布矩阵。而这条路径**只在 Windows 上存在**（非 win32 是 `no-relaunch-route`），跨平台抽象买不到东西 |
| **把内层命令当 argv 传给 `wscript`** | 实测失败：`node` 把参数里的双引号转义成反斜杠加引号，`wscript` 不还原 ⇒ `Shell.Run` 静默失败，症状只是「没有窗口」。改成传**路径**、命令放作业文件 |

## 已知限度

1. **端口是身份**。配置改端口后再重启，老窗口会看到「没有宿主」并在 5 秒后自行退出；
   下一次重启会带新端口起一个新窗口。降级是「一次重启内短暂没有停止按钮」，不会误杀。
2. **窗口被误关 = 宿主被停**。这是设计（它就是停止按钮）。没有二次确认——加确认会破坏
   「关掉终端就停掉」的原始直觉。
3. **进程名必须是 `node`** 才会被绑定。换运行时（如 bun / 独立 exe）需要同批改这条判据。
4. **`Add-Type` 首次编译约 1.2 s**：窗口出现比宿主慢一两秒，属可接受。
5. **`DSH_DEBUG_WINDOWLESS=1`** 由启动器注入给新宿主：今天没有消费者，它把「这个宿主没有
   控制台」变成可观测事实，而不是推断。
