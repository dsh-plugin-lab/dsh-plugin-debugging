本文件装两条互不相关的决策，因为它们同属「外围配置」这一档：一条管**测量**，一条管**去重**。

## 一、覆盖率起步取 wbb 档，不取官方「按文件 100%」

### 背景

官方测试文档里的覆盖率门禁是 **`pnpm run test:coverage`：门禁级运行，对 `packages/*/*/src`
按文件 100% 覆盖**（`[CK]\docs\testing.md:10`，`[CK]\docs\testing.zh.md:10`，2026-10-12 现读）。
**关键限定是那句 `packages/*/*/src`：这条门禁的对象是宿主自己的源码树**，
不是它对外发布的契约，也不是「第三方插件仓应当照抄的数字」。

同一段还写了另一半理由：*「未覆盖的行往往是门禁正确标记出的死代码（应删除），而非需要补写的测试。
行覆盖率是必要条件，但永远不是充分条件：它证明行被执行过，不证明功能按交付预期工作。」*
——**按文件 100% 是宿主用来抓死代码的**，它假定那棵树已经被大量测试覆盖；把它直接搬到
一个刚起步的插件仓上，得到的只会是一堆为了凑数字而写的断言。

姊妹仓 `dsh-workbuddy-bridge` 是唯一配了覆盖率门禁的仓，取的是
`provider: 'v8'`、`include: ['src/**/*.{ts,tsx}']`、
`thresholds: { lines: 70, statements: 70, functions: 60, branches: 60 }`
（`dsh-workbuddy-bridge/vitest.config.ts:78-83`，2026-10-12 现读）。

### 决定

**起步取 wbb 那一档**：lines / statements **70**，functions / branches **60**。

### 替代方案与被否的理由

- **照官方按文件 100%** —— 被否：门禁对象不同（见上）。它不是「更严所以更好」，
  而是**为另一个问题设计的**；照搬到起步仓会把人逼去写无价值的断言，而断言的边际价值为零时，
  它只会掩盖真问题。
- **先不设门禁，等测试够多再说** —— 被否：那等于把「什么时候算够」交给感觉。
  有档位至少让「覆盖率掉下去」这件事在某个具体数字上可见。
- **一次设到 100% 再往下调** —— 被否：门禁一开始就是红的等于没有门禁（人人都学会忽略它）。

### 代价与重开条件（**执行体未落**）

**当前现实：`vitest.config.ts` 里没有任何 `coverage` 配置**（2026-10-12 现读）——
所以本条**决定已定、执行体未落**，覆盖率此刻是**不测量**的。

**触发条件（任一成立就落）**：
- 给本仓加第一个覆盖率门禁时，按上面这一档设；
- 或首次发现**覆盖率盲区**（某段该被测的逻辑一直没有断言，而它已经出过一次错）——
  那时「先把它量出来」比继续凭感觉补测试更值。

**落的时候连带两件事**（否则门禁跑不起来）：
1. `@vitest/coverage-v8` **当前不在 devDependencies 里**（2026-10-12 现读；
   `node_modules/@vitest/coverage-v8` 也不存在）——加覆盖率要**同时加这个依赖**，
   而 npm 12 会拦 postinstall，装带安装脚本的依赖前要先明确 `allowScripts`
   （本仓 `AGENTS.md` 的「活跃坑」第 10 条）。
2. wbb 那份配置带 `exclude: ['lib/**', 'tests/**', 'node_modules/**', '**/*.d.ts']` ——
   漏掉 `lib/**` 会让**构建产物**被计入分子/分母，数字随一次 build 变动而**源码一行没改**。

**重开条件**：本仓测试体量接近姊妹仓、或按文件覆盖率稳定在档位之上时，再评估是否抬档。

## 二、撤掉本机个人目录里那份同名技能

### 背景

本机有一条**个人级**技能与本仓随包分发的那份**字节相同**：

- 本仓 `skills/dsh-plugin-debugging/SKILL.md`
- `~\.agents\skills\dsh-plugin-debugging\SKILL.md`

SHA256 实测**完全相同**：`9DE75AA711486C373079DB3D43E0AD431665750BA519BC5C885171FB8A14FE25`
（2026-10-12 直接对两个文件现算；与 recon-A「既成事实 F1」记的那份参考件同一哈希）。

个人级那份落在 user-agents 根，**rank 500**；本插件的 runtime 注册恒为 **250**，
升序小者胜 —— 所以插件上线后**压过**它（rank 方向与分层规则见
`2026-10-12-runtime-skill-registration-at-rank-250.md`）。用户当时的答复也点了这一层：
「只是因为会搞混，实际上技术上会被覆盖没问题」。

### 决定

**撤掉本机那份个人级副本**，让这份知识只有**一个来源**（本仓随包分发的那份）。

### 替代方案与被否的理由

- **两份都留着（靠 rank 决定谁生效）** —— 被否：技术上确实会覆盖，但**留下的是两份同源知识的
  漂移面**。本仓的 SKILL.md 会随版本演进，而个人目录那份不会；一旦有人改错或改了没同步，
  就会出现「插件里是新版、个人目录是旧版」而**谁生效取决于挂载位置**的局面。
  更糟的是被 shadow 是**完全静默**的（没有 API 能列出被遮蔽者）——
  读到旧版的人不会收到任何信号。
- **改个人级那份为「指针」** —— 被否：多一层间接，且仍然是一份要维护的副本；
  不如直接撤掉。

### 代价与重开条件（**顺序约束是硬的**）

**顺序约束：只有在本插件技能于隔离实例上被证明真的赢（真机阶梯 **S2** 通过）之后，才撤那份个人级副本。**
理由：S2 证明之前，「插件那份能不能挂上、rank 250 是否真的压过 500」**都还没被验证过**。
若先撤再验，而插件那条链又坏了（路径解析错、frontmatter 解析失败、被更高优先级的层 shadow），
就会出现一个**两份都不生效**的窗口 —— 排障知识在最需要它的时刻整体消失，
而且**不会有任何报错**（装载失败是静默的）。**先证明新的活着，再拆旧的。**

S2 的判据与做法（recon-A 一·2、`docs/ARCHITECTURE.md` 第 8 节的真机阶梯）：
隔离实例里放三份同名技能（项目级 / 用户级 / 本插件 runtime 注册），各写**可区分的 description**，
读 catalog 的 `provider` / `source` 字段判谁赢；预期是**赢 400/500、让位 100/200**。

**代价**：S2 通过之前，本机同时存在两份同名技能 —— 这段时间里
「我改的是哪一份」需要自己清楚（改本仓那份，个人级那份不要动）。

**重开条件**：不需要重开。这是一次性的本机清理；唯一的前置就是 S2。
（若将来本仓技能改为不随包分发，则本决策随之作废。）
